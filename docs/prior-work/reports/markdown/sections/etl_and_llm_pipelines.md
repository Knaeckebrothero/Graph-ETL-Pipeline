# 7. ETL and LLM Pipelines

The previous sections established what the knowledge graph should contain (Section 4), where the data would come from (Section 5), and why a vocabulary foundation should be laid before anything else (Section 6). What remained was the machinery to actually populate the graph from the 68 evaluated sources. These sources fell into two distinct categories: structured data — CSV files, JSON APIs, JSONL dumps, database exports — where the mapping from source fields to graph properties is deterministic, and unstructured documents — PDFs of legal texts, municipal waste guides, German-language regulations — where a language model must interpret prose and extract entities, relationships, and conditional logic. This duality motivated two parallel pipeline architectures.

## 7.1 Structured ETL

The structured pipeline (`src/etl/`) handles sources with known schemas through deterministic Python scripts. Each script reads a specific data format, transforms it into the graph ontology, and writes to Neo4j using MERGE queries for idempotent re-runs. The facility import parses a JSON file of disposal locations into Facility nodes with addresses, opening hours, and contact information. The waste item import reads a CSV of the Abfall-ABC into WasteItem nodes with disposal relationships. The dictionary pipeline described in Section 6 — the most complex structured import — processes over a million JSONL entries through concept clustering and batch import. Additional structured modules handle the AVV code hierarchy and the material taxonomy for product decomposition.

These pipelines share a common pattern: read the source, filter and transform in Python, write to Neo4j with MERGE-based idempotency. No LLM is involved. The code is fast (the entire dictionary imports in under a minute), deterministic (identical output on every run), and cheap (no API costs). For sources that arrive as structured data, this is always the preferred approach. The LLM pipeline exists for the sources where deterministic mapping is not possible.

## 7.2 Schema-Driven LLM Extraction

The central idea behind the LLM extraction pipeline is that the data model itself should drive the extraction. Rather than writing source-specific parsing logic for each document type, we defined Pydantic models — one for each entity type in the graph ontology — whose field names and descriptions serve simultaneously as the extraction schema and the LLM prompt. A `WasteItemExtract` model with a field `disposal_targets: list[str]` described as "Names of facilities or waste streams where this item should be disposed" tells the language model exactly what to look for, and Pydantic's validation ensures the output conforms to the expected structure.

The `ExtractionChain` is the workhorse component. It is stateless: given a block of text, a Pydantic schema, and optionally an extraction prompt and context string, it returns a list of validated entity instances. Internally, it wraps the schema in a list container (to handle documents containing multiple entities), constructs a prompt from the schema's field descriptions, and calls the language model with LangChain's structured output mechanism. If the model returns malformed output, the chain retries with the validation error as feedback — typically once is sufficient to correct formatting issues.

The schema registry provides six extraction types that map to the graph ontology: `WasteItemExtract` for waste items with disposal targets and conditions, `FacilityExtract` for disposal locations with addresses and opening hours, `WasteStreamExtract` for bin types with physical descriptions, `DisposalRuleExtract` for conditional disposal logic (the "Paint Can" problem from Section 1.2 modeled as structured data), `RelationshipExtract` for connections between existing entities, and `SourceExtract` for provenance metadata. For domain-specific extraction tasks that do not fit these types — chemical compound identification, construction material classification — custom Pydantic models can be defined without modifying the pipeline code. A `GenericEntityLoader` handles any Pydantic model by creating labeled Neo4j nodes using the class name as the node label and serializing all fields as properties.

## 7.3 Two Modes: Chain and Agent

The `Pipeline` class — the recommended entry point for both notebook use and programmatic access — offers two execution modes that trade speed for thoroughness.

**Chain mode** executes a single LLM call: text goes in, validated entities come out, and an optional database load persists the results with provenance tracking. This is fast (one API round-trip), deterministic at temperature zero, and suitable for well-understood document types where the extraction schema closely matches the source structure. A batch of Abfall-ABC entries, for instance, maps cleanly to `WasteItemExtract` without needing any additional context.

**Agent mode** interposes a multi-turn exploration phase before extraction. A LangGraph ReAct agent receives the input text and five read-only tools for inspecting the existing knowledge graph: `search_entities` lists entities of a given type, `get_entity_details` retrieves a specific node's properties, `get_graph_stats` returns node and relationship counts, `list_waste_streams` enumerates all bin types, and `list_facilities` enumerates all disposal locations. The agent uses these tools to build context about what already exists in the database, then passes this context — along with the original text — to the ExtractionChain for the actual extraction.

The practical difference is entity resolution accuracy. In chain mode, the pipeline might extract a facility name as "Wertstoffhof Frankfurt-Nord" when the graph already contains the same facility as "Wertstoffhof Nord" — creating a near-duplicate that would require post-hoc deduplication. In agent mode, the agent discovers the existing name during its exploration phase and the extraction uses the canonical form. This graph-awareness comes at the cost of multiple LLM calls (several tool-use rounds before extraction begins), making agent mode significantly slower than chain mode. The choice depends on the source: high-volume structured imports use chain mode; complex documents with many cross-references to existing entities use agent mode.

## 7.4 The Orchestrator

For processing longer documents that contain multiple entity types — a municipal waste guide, for instance, that mentions facilities, waste items, disposal rules, and bin types in the same PDF — the orchestrator provides a four-stage LangGraph state machine.

**Analyze:** Compute document statistics, detect likely entity types via German keyword heuristics (terms like "Entsorgung," "Wertstoffhof," and "Biotonne" trigger different schema selections), and chunk the document into processable segments. The paragraph chunking strategy proved most reliable for German regulatory documents, which tend to organize information by topic within paragraphs.

**Plan:** Map the detected entity types to schemas from the registry, query the database for existing entities of each type (providing context for deduplication), and create an ordered extraction plan — WasteItems first, since they are the most common entity type and downstream rules and relationships reference them.

**Extract:** Iterate through the plan, running the ExtractionChain for each chunk and schema combination. A document chunked into 12 paragraphs with 3 detected entity types produces up to 36 extraction calls, though in practice many chunks yield no entities for a given schema.

**Validate:** Check each extracted entity against database constraints — do the referenced facility names exist? Are the disposal target names valid waste streams? — and produce a gap analysis identifying new entities, matches to existing ones, and database-only entities not found in the document. This validation step catches extraction errors before they reach the database.

## 7.5 Provenance and Idempotency

Section 4.5 introduced provenance tracking as a cross-cutting concern in the schema. The pipeline implementation makes this concrete through two mechanisms. First, deterministic UIDs: every entity receives a UID generated from the SHA256 hash of its canonical name, truncated to 16 characters. The same waste item extracted from different documents or at different times always resolves to the same Neo4j node, making re-runs safe — the MERGE pattern updates existing nodes without creating duplicates. Second, the EntityLoader distinguishes between three actions — creation (new node), update (existing node with changed properties), and enrichment (existing node receiving additional properties from a new source) — tracking each in a structured `LoadResult` that reports exactly what changed. When extraction quality improves through better models or refined prompts, the provenance trail identifies which entities came from which source, enabling targeted re-extraction without rebuilding the entire graph.

## 7.6 Models and Cost

The pipeline supports any OpenAI-compatible API endpoint, configured through environment variables (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`). In practice, we used three model tiers depending on the task.

For reasoning-heavy extraction — documents containing conditional disposal logic, multi-step classification, or ambiguous German regulatory prose — we used the GPT-OSS-120B reasoning model described in Section 3.2. Its explicit chain-of-thought significantly improved extraction quality for complex disposal rules compared to non-reasoning alternatives, particularly for identifying condition branches ("if the paint is still liquid" versus "if the can is empty and dry").

For high-volume batch classification — the dictionary baseline's 92,000 concept clusters (Section 6.4) and the AVV code hierarchy — we used Llama 3.1 8B via Groq. Groq's inference speed made it practical to classify hundreds of thousands of entries at approximately $0.30 per 100,000 items. The tradeoff was lower reasoning capability, acceptable for binary classifications (`is_physical`, `disposal_relevant`) but insufficient for nuanced extraction tasks.

GPT-4o served as the default for development and testing, providing a balance between capability and cost. The provider abstraction means that switching models requires changing a single environment variable — no code modifications.

## 7.7 Extending the Pipeline

The pipeline was designed so that future semesters can add data sources without modifying the extraction framework itself. The process follows a repeatable pattern: define a Pydantic schema for the target entities (or reuse an existing one from the registry), write an extraction prompt describing what to look for, choose a mode (chain for structured or well-understood sources, agent for sources requiring graph context), run the pipeline against the source documents, and review the load results before committing to the database.

Prompt design follows a few practical guidelines we developed through iteration. Effective extraction prompts are specific about the target domain ("Extract waste items mentioned in this German municipal waste guide") rather than generic ("Extract entities"). They name the expected output format by referencing schema fields ("Include disposal_targets as facility or bin names"). And they constrain the language when relevant ("Preserve German terminology for waste item names; do not translate"). The `dry_run` option — available on both the Pipeline and the EntityLoader — executes the full extraction and validation pipeline without writing to Neo4j, allowing prompt iteration against real documents before any data enters the graph. In practice, two to three dry-run iterations were typically sufficient to refine an extraction prompt from producing noisy, partially correct output to producing clean, loadable entities. The subsequent sections describe how this pattern was applied to specific data sources: the dictionary baseline (Section 6, already described), Open Food Facts products, AVV code classification, and office item imports.
